## Executive Summary

This deliverable defines the design of the SKAVA Data Discovery and Access layer. The design addresses the need for astronomers and scientific users to search, identify, retrieve, and access SKA-related datasets distributed across SKA Regional Centres (SRCs) and other heterogeneous storage locations.

The proposed architecture is metadata-driven, VO-aligned, and designed around a separation between:

- scientific discovery of datasets;
- distributed replica and node modelling;
- access resolution and routing;
- future data subsetting and processing services;
- operational observability and security controls.

The design was used as the basis for the later T3.2 implementation. In the implemented system, the core concepts are realised through a FastAPI service, a PostgreSQL metadata catalogue, an ObsCore-oriented dataset model, DataLink-like access descriptors, a minimal TAP sync ObsCore compatibility profile, SODA-oriented orchestration stubs, structured logging, health checks, and Prometheus metrics.

The current design intentionally distinguishes between implemented production-hardened features and planned full-standard capabilities. In particular, the design supports a clear evolution path toward full TAP/ObsTAP, DataLink, SODA execution, SRC federation, advanced data staging, and large-scale data locality optimisation.

## 1. Scope and Objectives

### 1.1 Scope

The scope of D3.1 is the design of the SKAVA Data Discovery and Access subsystem. This subsystem is responsible for enabling users and client applications to:

- discover SKA datasets through scientific metadata;
- filter datasets by spatial, spectral, temporal, collection, product, and identifier constraints;
- inspect dataset placement across distributed storage nodes;
- resolve the most appropriate access endpoint for a dataset;
- expose VO-aligned service descriptions;
- support future integration with SKA Regional Centres and distributed compute/storage environments.

The scope does not include the final implementation of visual analytics interfaces, which is handled in a separate task.

### 1.2 Objectives

The main objectives are:

- provide a robust metadata-driven discovery architecture;
- support distributed data access across SRC-like nodes;
- keep the system compatible with astronomy community standards;
- reduce latency through replica-aware routing and data-locality design;
- support Open Science and FAIR principles;
- provide an extensible foundation for petascale and exascale SKA scenarios;
- provide clear operational boundaries between current capability and planned future extensions.

## 2. Scientific and Operational Requirements

### 2.1 Scientific Requirements

The system must support scientific workflows typical of SKA data analysis:

- discovery of calibrated science products;
- filtering by sky position;
- filtering by time interval;
- filtering by spectral interval;
- filtering by observation collection and product type;
- support for multiple data product classes, including images, cubes, catalogues, time-domain products, and future visibility-derived products;
- compatibility with VO-oriented tooling and notebook-based analysis workflows.

### 2.2 Operational Requirements

The system must:

- operate with distributed data placement;
- avoid requiring bulk data movement during discovery;
- expose stable APIs for automated clients;
- support health checks and monitoring;
- provide bounded query behaviour;
- provide structured error responses;
- support future authentication and authorisation integration;
- preserve the ability to evolve without breaking existing clients.

### 2.3 Non-Functional Requirements

The design addresses:

- scalability: support growth from prototype catalogues to large SRC metadata catalogues;
- interoperability: align with IVOA concepts and protocols;
- maintainability: modular services, clear schema boundaries, explicit capability declarations;
- reliability: health checks, fallback routing, structured errors;
- reproducibility: metadata, source references, checksums, and planned provenance support;
- security: internal ingestion control, future user-level access control, and safe exposure of public replicas.

## 3. Architectural Principles

The design is based on the following principles.

### 3.1 Metadata-Driven Discovery

Discovery must operate on metadata, not on raw data files. This enables low-latency search and prevents expensive scans across large FITS files, cubes, catalogues, or object stores.

### 3.2 Separation of Discovery and Access

Discovery identifies candidate datasets. Access resolution selects a usable endpoint and returns an access contract. This avoids coupling search semantics to transport/storage implementations.

### 3.3 VO Alignment without Premature Full Compliance Claims

The design aligns with ObsCore, TAP, DataLink, SODA, and VOSI concepts. Full compliance is treated as an evolution path. This allows useful production-oriented services while keeping the architecture compatible with future full-standard implementations.

### 3.4 Data Locality and Replica Awareness

Datasets may exist on multiple nodes. The access layer must rank replicas using availability, accessibility, latency, load, and capability signals.

### 3.5 Bounded Query Behaviour

Queries must be bounded by limits, pagination, and validation. This is essential for large catalogues and production services.

### 3.6 Extensibility

The architecture must allow future additions:

- full TAP/ADQL;
- async TAP;
- full DataLink service responses;
- SODA subsetting execution;
- SRC federation;
- caching and staging;
- provenance services;
- DOI/PID integration.

## 4. High-Level Architecture

The Data Discovery and Access layer is structured as a service-oriented backend with the following logical components:

1. API layer
2. Discovery service
3. Metadata catalogue
4. Replica and node catalogue
5. Ranking and routing policy
6. DataLink/access descriptor layer
7. TAP/ObsCore compatibility layer
8. SODA orchestration layer
9. Ingestion layer
10. Observability and health layer

### 4.1 Logical Data Flow

The intended flow is:

1. A user or client submits a discovery query.
2. The API layer validates scientific parameters.
3. The discovery service queries the metadata catalogue.
4. Candidate datasets are matched against spatial, spectral, temporal, and product filters.
5. Replica metadata is loaded for the matching datasets.
6. The ranking policy filters and ranks eligible replicas.
7. The response returns scientific metadata, available replicas, and an access descriptor.
8. The user requests access for a selected dataset.
9. The access layer resolves the best available endpoint and returns a DataLink-like contract.
10. Future SODA/DataLink services execute subsetting, staging, or transfer jobs.

### 4.2 Physical Deployment Model

The implementation baseline uses:

- FastAPI application server;
- PostgreSQL metadata database;
- Docker deployment;
- optional reverse proxy for staging/production ingress;
- environment-driven configuration;
- Prometheus metrics endpoint;
- structured JSON logs.

This deployment can evolve to multiple replicated API instances behind a load balancer, with PostgreSQL high availability or a distributed metadata backend.

## 5. Metadata and Data Model Design

### 5.1 Core Entities

The design defines three core entities.

#### Dataset

Represents a scientific observation or data product. It follows practical ObsCore-style naming:

- `obs_id`
- `obs_collection`
- `obs_title`
- `dataproduct_type`
- `calib_level`
- `target_name`
- `facility_name`
- `instrument_name`
- `s_ra`
- `s_dec`
- `s_fov`
- `t_min`
- `t_max`
- `em_min`
- `em_max`
- `access_format`
- `access_estsize`
- `source_ref`
- `source_type`
- `checksum`

#### Node

Represents a storage or SRC-like access node:

- node code and name;
- base URL;
- enabled/available flags;
- latency score;
- load score;
- capability score.

#### Dataset Replica

Represents physical or logical placement of a dataset:

- dataset reference;
- node reference;
- remote path;
- access endpoint;
- replica status;
- public accessibility flag.

### 5.2 Metadata Design Rationale

The metadata design intentionally starts with a compact ObsCore-aligned subset. This supports immediate discovery while keeping room for future extension to:

- richer spatial footprints;
- MOC/HEALPix coverage;
- polarization metadata;
- data quality fields;
- provenance chains;
- calibration versioning;
- project/proposal identifiers;
- rights and embargo metadata;
- DOI/PID metadata.

## 6. Scientific Discovery Design

### 6.1 Discovery API

The primary discovery endpoint is:

- `GET /discovery/search`

Supported scientific parameters:

- `POS`
- `BAND`
- `TIME`
- `COLLECTION`
- `DPTYPE`
- `obs_id`
- `limit`
- `offset`
- `SPATIAL_CELL`

All scientific filters are combined using AND semantics.

### 6.2 Spatial Query Design

The baseline supports:

- `POS=CIRCLE <ra> <dec> <radius>`

The design uses centre-based overlap with optional field-of-view expansion. This is a pragmatic initial design for production-safe metadata filtering, not a full spherical geometry implementation.

Evolution path:

- support additional VO region shapes;
- implement accurate spherical geometry;
- introduce MOC/HEALPix indexing;
- support large-area survey footprint discovery.

### 6.3 Spectral Query Design

The baseline supports:

- `BAND=<min> <max>`

The query matches overlap against dataset `em_min` and `em_max`.

### 6.4 Temporal Query Design

The baseline supports:

- `TIME=<min> <max>`

The query matches overlap against dataset `t_min` and `t_max`.

### 6.5 Query Safety

Discovery queries are bounded by:

- default `limit=100`;
- maximum `limit=1000`;
- `offset` validation;
- structured `400` errors for malformed parameters.

This design prevents unbounded result scans and provides predictable behaviour for client applications.

## 7. Indexing and Search Strategy

### 7.1 Baseline Indexing

The baseline metadata catalogue uses indexes on:

- observation identifier;
- collection;
- data product type;
- spatial coordinates;
- spectral bounds;
- temporal bounds;
- replica dataset and node references.
- lightweight spatial cell keys.

### 7.2 Planned Advanced Indexing

For SKA-scale catalogues, the design foresees:

- HEALPix or MOC-based spatial indexing;
- composite indexes for common query combinations;
- partitioning by collection, time, or survey;
- materialised metadata views for high-demand products;
- search backend integration for text/faceted discovery;
- cost-aware query planning for federated catalogues.

## 8. Distributed Data Access Design

### 8.1 Access Resolution

Access resolution is separated from discovery. The main access endpoints are:

- `GET /discovery/dataset/{obs_id}`
- `GET /datalink/{obs_id}`
- `GET /access/{obs_id}`

`/datalink/{obs_id}` is the canonical access descriptor endpoint.

`/access/{obs_id}` is a compatibility facade for clients expecting a simpler routing contract.

### 8.2 Replica Eligibility

A replica is eligible when:

- its status is `available`;
- it is marked public for public access flows;
- its node is enabled;
- its node is available;
- its access endpoint is valid.

### 8.3 Replica Ranking

The ranking policy prioritises:

1. lower latency score;
2. lower load score;
3. higher capability score.

This provides a deterministic and extensible ranking model. Future versions may include:

- geographic or network proximity;
- user location;
- quota and policy constraints;
- data-locality relative to compute resources;
- cost-aware transfer estimation;
- historical reliability.

### 8.4 Access Contract

The access contract contains:

- selected best node;
- primary access URL;
- alternate replicas;
- dataset identity;
- format and estimated size;
- service descriptors;
- capability flags.

The contract avoids streaming data directly through the discovery service. This preserves scalability and allows storage-specific transfer mechanisms.

## 9. VO and Interoperability Design

### 9.1 ObsCore Alignment

The design adopts ObsCore-style metadata fields for discovery. This allows evolution toward ObsTAP without changing the core dataset representation.

### 9.2 TAP/ObsTAP

The current design provides a minimal TAP sync compatibility profile:

- `GET /tap/capabilities`
- `GET /tap/sync`
- `POST /tap/sync`
- `POST /tap/async`
- `GET /tap/async/{job_id}`

The supported query profile is intentionally constrained:

- `SELECT` from `ivoa.ObsCore`;
- equality predicates on `obs_id`, `obs_collection`, and `dataproduct_type`;
- bounded `MAXREC`;
- VOTable output by default;
- JSON output when requested.
- persisted async job records for longer-running query execution profiles.

Evolution path:

- full ADQL parser/execution;
- async TAP;
- richer ObsCore table exposure;
- TAP_SCHEMA;
- VO registry integration.

### 9.3 DataLink

The design provides:

- JSON access descriptor;
- minimal VOTable links table;
- primary and alternate access links;
- service descriptors for access resolution and SODA-oriented operations.

Full DataLink compliance remains a planned extension.

### 9.4 SODA

The design exposes a SODA-oriented sync endpoint as an orchestration stub:

- validates `ID`, `POS`, `BAND`, `TIME`, `RESPONSEFORMAT`;
- resolves routing;
- returns a structured response describing planned subsetting.

Actual server-side cutout/subset execution is deferred to future work.

### 9.5 VOSI-Inspired Capabilities

The service exposes capabilities metadata to describe:

- available endpoints;
- supported parameters;
- standards alignment;
- current support level.

## 10. Security and Access Control Design

### 10.1 Current Security Baseline

The design includes:

## 12. Performance and Scalability Design

### 12.1 Baseline Scalability Controls

The design includes:

- database indexing;
- bounded result sets;
- pagination;
- eager loading of replica metadata;
- replica-aware routing;
- health and metrics endpoints;
- stateless API services that can be horizontally scaled.

### 12.2 Large-Scale SKA Evolution

For TB/PB/exascale environments, the architecture should evolve with:

- partitioned metadata catalogues;
- distributed query brokers;
- metadata caching;
- asynchronous query execution;
- data staging workflows;
- near-data compute scheduling;
- object storage and HPC transfer integration;
- transfer cost estimation;
- adaptive routing based on live telemetry.

## 13. Caching, Prefetching, and Data Locality

The design separates three levels of optimisation.

### 13.1 Metadata Caching

Frequently accessed metadata and capability responses can be cached at API or reverse proxy level.

### 13.2 Access Routing Cache

Replica ranking decisions may be cached with short TTLs when node status and load telemetry are stable.

### 13.3 Data Staging and Prefetching

For future production use, large data products should be staged using asynchronous workflows:

- user requests dataset access;
- system estimates best replica and transfer path;
- staging job prepares data near compute or notebook environment;
- user receives status and final access URL;
- cache eviction follows policy and quota constraints.

## 14. Ingestion Design

The ingestion subsystem loads metadata manifests and normalises them into the internal ObsCore-oriented model.

Supported concepts:

- CSV and JSON manifests;
- dry-run validation;
- execution history;
- required field validation;
- coordinate and interval validation;
- access URL validation;
- update of existing datasets and replicas.

The ingestion design supports future integration with SRC metadata harvesters, VO registries, and automated survey pipelines.

## 17. Risks and Mitigation Strategy

### 17.1 Risk: Full VO Compliance Not Yet Complete

Mitigation:

- keep support-level declarations explicit;
- provide minimal compatible profiles;
- evolve toward full TAP/DataLink/SODA with tests.

### 17.2 Risk: Centralised Metadata Catalogue Bottleneck

Mitigation:

- add partitioning;
- introduce caching;
- design federated query broker;
- integrate SRC metadata harvesting.

### 17.3 Risk: Spatial Query Approximation

Mitigation:

- introduce MOC/HEALPix;
- support full VO region geometry;
- validate against astronomy use cases.

### 17.4 Risk: Access Control Insufficient for Proprietary Data

Mitigation:

- add authentication and authorisation;
- implement policy-aware replica filtering;
- support delegated credentials and audit logs.

### 17.5 Risk: Large Data Movement Costs

Mitigation:

- avoid data movement in discovery;
- introduce staging and transfer planning;
- favour compute-near-data workflows.

## 19. Conclusion

The D3.1 design defines a pragmatic and extensible architecture for SKAVA data discovery and access. It provides a metadata-driven foundation aligned with astronomy standards while preserving a clear path toward full SRC-scale interoperability and production deployment.

The later T3.2 implementation follows this design by delivering the core backend services: discovery, access routing, replica ranking, DataLink-like descriptors, VOTable output, minimal TAP sync support, SODA orchestration stubs, ingestion, monitoring, and operational hardening.

The design should be considered a production-hardened baseline rather than a final SKA production-scale platform. Full production readiness requires the planned extensions for federated SRC operation, complete VO compliance, SODA execution, stronger security, provenance, PID/DOI support, and performance validation at SKA data scale.
